## Scope

M008 selects the cookie-session portion of FR-001/002, API-AC-002/003/012/014 and V-004/V-009/V-015. M007 is complete and supplies durable confirmed/unconfirmed ASP.NET Core Identity accounts, exact password handling, persistent Data Protection keys, the `VerifiedAccount` current-state policy, real SQLite integration support and deterministic contract generation.

The milestone adds four account operations with these stable names and wire boundaries:

- `GET /api/accounts/antiforgery` (`getAccountAntiforgeryToken`) is anonymous and returns `200 { "requestToken": "...", "headerName": "X-LinguaDesk-Antiforgery" }`. It sets only the host-scoped antiforgery cookie `__Host-LinguaDesk.Antiforgery`, configured Secure, HttpOnly, SameSite=Strict and Path=/, and exposes no account state. The SPA sends the returned token in `X-LinguaDesk-Antiforgery` with the matching cookie. Calling bootstrap after an identity change replaces the usable request-token pair.
- `POST /api/accounts/sign-in` (`signInLocalAccount`) requires the valid antiforgery cookie/header pair and accepts exactly required string fields `email` and `password`, with no query parameters or mode/remember-me field. Email follows M006 syntax and the password is passed to Identity exactly as supplied without trim, normalization or truncation. Valid credentials return `200 { "status": "signedIn", "verificationStatus": "verified" | "verificationRequired", "expiresAtUtc": "..." }` and issue only the browser session cookie. Unknown email and wrong password return the same `401` Problem Details category `invalidCredentials`; only valid credentials may disclose `verificationRequired`. Storage/key/signing failure is a sanitized `503`/`availability` result and issues no usable session.
- `GET /api/accounts/session` (`getLocalAccountSession`) uses the real cookie handler and returns the same status, verification status and fixed server-ticket expiry for the current account. Missing, expired, malformed, deleted or security-stamp-invalid credentials return no account data and the same no-store `401` category `authenticationRequired`, never an HTML redirect. No cookie is renewed by this read.
- `POST /api/accounts/sign-out` (`signOutLocalAccount`) requires a valid antiforgery pair, is safe for authenticated or already signed-out callers, clears `__Host-LinguaDesk.Session`, returns an empty `204`, and changes no security stamp. Repeating it with a fresh anonymous bootstrap pair remains 204. Server loss does not alter M013's later obligation to clear workspace text immediately on the client.

The session cookie name is `__Host-LinguaDesk.Session`, with Secure, HttpOnly, SameSite=Lax and Path=/ attributes. It is a nonpersistent browser session cookie: no Expires/Max-Age or remember-me option is emitted. Its protected server ticket expires exactly eight hours after issue, uses UTC from the injected time source and has sliding renewal disabled. The response's `expiresAtUtc` reports that ticket expiry; it is not a promise that a browser will retain the cookie until then.

Authentication runs before authorization. Every accepted cookie access loads the current account and compares the credential security stamp on that request; no default validation interval may delay rejection. The current model has no separate enabled flag. A deleted account or changed stamp therefore invalidates the next session read/protected request. A request carrying an `Authorization: Bearer ...` header must never fall back to an ambient valid cookie; until M009 supplies bearer authentication it receives an authentication failure. An unverified account may hold a cookie and read `verificationRequired`, but the existing fresh-state `VerifiedAccount` policy still denies language admission.

Account responses and errors use `Cache-Control: no-store`. Antiforgery failures use a secret-free `400` Problem Details category `invalidAntiforgery`; strict JSON/media/query/method failures follow the existing account boundary and never echo email, password, cookie, request token or raw Identity errors. Sign-in and sign-out accept POST only, session/bootstrap accept GET only, and wrong methods return 405 with the single allowed method. No endpoint redirects.

Explicit exclusions: bearer/access/refresh issuance and refresh concurrency, password reset or stamp mutation, account deletion/disable UI, per-device or copied-token revocation, browser forms/routes/safe-return logic/workspace teardown, language operations, allowances/accounting, live email, roles/admin/Google/OAuth/OIDC/JWT, P-005 attempt controls and P-006 compatibility guarantees. M009/M010/M013/M034 retain those outcomes. M008 does not complete full FR-001/002, API-AC-002/003, RG-005 or any release gate.

## Constraints and decisions

Use the real ASP.NET Core Identity cookie handler, password verifier, security stamps, antiforgery services, production SQLite provider/migrations and persistent Data Protection keys. A test-auth principal, mocked user store, manually fabricated cookie or synthetic antiforgery check cannot establish AC-001–005. Focused tests use fake time and owned HTTPS/file-backed fixtures; no sleep or public service is needed.

No email, password, cookie/ticket, antiforgery token, user ID, security stamp, query string or raw Identity exception may enter response details, logs, traces, filenames, test reports or committed fixtures. Safe diagnostics contain only category, correlation and classified outcome. All account responses are non-cacheable; this slice persists no new account, session or text data and needs no migration or package.

Q-006 is resolved locally for these four operations, names, fields, cookie/header policy and error categories. Q-004 does not block the bounded cookie behavior: M008 claims only caller-cookie clearing and current stamp/account validation, not account deletion semantics, backup retention or revocation of other sessions. P-005/NFR-008 and P-006 remain proposed, so no attempt limiter or version guarantee is introduced. Human/live browser evidence belongs to M013 and is not replaced by deterministic API tests.
