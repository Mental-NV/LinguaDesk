# M047 — Implementation plan

Behavior: [spec](spec.md). Reviewed inputs: [manifest](context.json). Implementation is not part of this planning change.

## Execution brief

Add GitHub Actions for the existing .NET 10/React combined publish output. Provision two isolated resource groups with Bicep, one each for GitHub environments `Staging` and `Production`. Each contains a Linux F1 App Service Plan, Web App, workspace-based Application Insights component and dedicated Log Analytics workspace; never share databases, keys, telemetry or deployment identities. Deploy PR head revisions to Staging and main push revisions to Production. Use OIDC, idempotent Bicep provisioning and prebuilt ZIP artifacts; no deployment slots. Non-secret settings live in versioned configuration or are derived automatically. GitHub requires zero environment/repository variables and only one environment secret name, `DEEPSEEK_API_KEY`, with separate values for Staging and Production.

Preserve existing API contracts and UI behavior. A one-time bootstrap uses authenticated Azure CLI and GitHub CLI sessions to establish resource groups, OIDC and GitHub environments and generate non-secret deployment identifiers. Repository implementation can proceed without Azure credentials; hosted acceptance requires authorized bootstrap access and provider secret values. This rewrite remains a planning change, not an instruction to execute cloud deployment now.

## Changes and order

### 1. Linux SQLite hosting profile and release preparation

Update `StorageOptions`, persistence connection/initialization policy, deployment tooling and focused API persistence tests. Add an explicit `Storage:JournalMode` option: retain WAL for existing local deployments; select `Delete` for App Service and use `synchronous=FULL`, foreign keys and bounded busy timeout. Reject unknown modes and unexpected existing database modes before serving. Do not rewrite applied migrations.

The initial migration currently forces WAL. Build a dedicated deployment preparation mode/tool that runs before the web host, against the mounted target file: provision directories with restrictive permissions, acquire an exclusive deployment lock, retain a consistent backup, apply EF migrations, checkpoint any legacy WAL and switch to DELETE with no other connections open, assert actual journal mode and database integrity, then release the lock. Test fresh initialization and upgrades through the existing WAL-setting migration. Never serve while transient migration journal settings are active. Local normal startup still does not mutate schema; the new deployment startup wrapper explicitly invokes preparation and then `exec`s the API. Migration failure exits without starting the host. Abrupt restarts must retry safely; don't assume a graceful shutdown hook will run.

Use `/home/linguadesk/data/linguadesk.db`, `/home/linguadesk/keys` and `/home/linguadesk/backups`, outside `/home/site/wwwroot`. Keys are durable and environment-specific. Never copy the live SQLite file to ephemeral local storage and periodically sync it back. Keep a single app process/instance; serialize all deployments and prevent old/new workers from overlapping database access during restart. A simple successful smoke does not prove network filesystem durability: hosted checks must exercise contention, interruption, restart, redeployment and restore, and inspect integrity/accounting invariants. If locking/durability fails on App Service storage, leave this AC blocked and record the failure for a design decision; no automatic fallback to volatile storage or a new database service.

### 3. Events, environment routing and credential boundaries

Draft PRs also deploy on those events; ready-for-review reruns are harmless. Checkout the exact `github.event.pull_request.head.sha` for PRs, `github.sha` for main pushes. Record that revision in the artifact. Checkout must not persist credentials.

All events run offline checks with `contents: read`. Staging deployment additionally requires a same-repository head and excludes Dependabot; fork/restricted PRs report a deliberate deploy skip. Production requires `event_name == push` and `ref == refs/heads/main`. Use separate jobs with literal `environment: Staging` / `environment: Production` and explicit `needs` on successful checks/package. There is no privileged `pull_request_target` or unvalidated `workflow_run` handoff.

Deployment jobs alone receive `id-token: write`, the selected environment secret and Azure login. Read subscription/tenant/client IDs from the generated non-secret deployment manifest, not GitHub variables. Bootstrap reads the repository OIDC subject settings through GitHub API before requesting keys or mutating resources. Require the default subject template and an explicit supported subject mode; validate the reported `sub_claim_prefix` against the selected repository. Immutable mode includes owner/repository IDs (`repo:OWNER@OWNER_ID/REPO@REPO_ID`); explicitly reported legacy mode uses `repo:OWNER/REPO`. Unknown, custom or mismatched settings fail closed rather than guessing. Pass the discovered prefix to Bicep and append only `:environment:Staging` or `:environment:Production` for each separate identity; place each identity and its federated credential in that environment's own resource group, as selected on 2026-10-28. Create no shared identity group. Grant an RG-scoped custom role with only resource-group reads, Bicep deployments, Web App/plan and Insights/workspace operations, including cap operations. Do not grant ManagedIdentity or Authorization writes; routine jobs cannot change their own trust, RBAC, subscription resources or the other environment. Bootstrap requires resource/custom-role creation and role-assignment permissions; routine jobs do not. Production GitHub environment restricts deployment branches to main; Staging permits the required PR refs. Keep required-reviewer rules off for the requested automatic deployment behavior. Verify repository plan supports configured environment protections.

Use build concurrency per PR or main with cancellation allowed. Deployment concurrency is per target environment with `cancel-in-progress: false`, so migration/deploy is not killed mid-operation. Recheck PR open state/head SHA or current main SHA immediately before mutation and skip stale artifacts. Serialize stop/infrastructure update/cap configuration/app-settings/ZIP/start/smoke in that same group. PR deployment may reconcile only Staging infrastructure; Production reconciliation runs only on main pushes. Shared Staging is the latest eligible PR deployment, not one preview per PR; a summary records PR number, SHA and URL. Closing a PR must not delete shared Staging.

### 4. Bicep, configuration and automated bootstrap

Provide `scripts/azure/find-f1-regions.sh` as a credential-free regional quota diagnostic after Azure login. Enumerate advertised Linux F1 regions, optionally restrict candidates, then validate one new uniquely named F1 plan per candidate with provider-level ARM validation in an existing group. Use a flat Bicep probe with no nested outputs/credentials so quota checks cannot be skipped through unresolved references. Do not reuse an existing plan as the probe. Bound parallel requests/timeouts, distinguish quota rejection from permission/policy/unknown failures, emit a table or JSON, and never create/delete resources, change regions, or read provider keys. A passing preflight is point-in-time evidence for one additional plan, not a reservation or a full app deployment.

Add `infra/azure/bootstrap.bicep` (subscription scope), `infra/azure/main.bicep` (environment resource-group scope), modules for App Service and monitoring, `infra/azure/staging.bicepparam`, `infra/azure/production.bicepparam`, and `scripts/azure/bootstrap.sh`. Pin supported resource API versions during implementation. Use `infra/azure/environments.json` as the shared Python/Bicep source for the exact names, regions and default hostnames in the selected spec. Production uses Sweden Central by explicit user direction after the authenticated F1 provider-validation scan; Staging uses Indonesia Central, matching the operator-updated configuration and recreated group/identity. Keep the F1 SKU, .NET stack, 30-day workspace retention and telemetry cap policy versioned. Check exact global name availability before mutation and reject an existing app in the wrong group or with the wrong hostname. Omit the secure-unique/hashed-hostname option and block activation unless Bicep returns `linguadesk.azurewebsites.net` / `staging-linguadesk.azurewebsites.net` exactly. Do not append a hash or substitute names, regions or SKUs. Consume resource IDs and monitoring connections directly from Bicep. During provisioning, pass the monitoring module output to the app module so ARM waits for Insights creation before reading its connection string. Only activation, which skips monitoring reconciliation, reads the existing component. Because ARM can short-circuit nested module validation when inputs depend on module outputs, also validate the App Service module directly with disposable dummy credentials/connection input; never apply those dummy parameters. Bootstrap validates both regional F1 allocations after group/identity creation and before GitHub configuration or runtime provisioning; routine deployment validates before stopping the app. Azure failures report allowlisted error codes and fixed remediation hints; never log raw diagnostic messages or secure parameter payloads.

Bootstrap reads subscription/tenant from the active `az` context and owner/repo from `gh repo view`. It uses Bicep to create exactly the two named environment resource groups, with each environment's user-assigned identity, federated credential and scoped custom role/assignment inside its own group. It generates `infra/azure/deployment.json` with only subscription ID, tenant ID, environment client IDs and resource-group names. This non-secret manifest is intended for source control and is generated, not hand-edited; bootstrap validates it before writing and never commits/pushes automatically. Rerunning for the same subscription/repository preserves identities and names. Both environment regions are fixed in the versioned naming configuration; no shared `--location` override or portal editing is required. The subscription deployment metadata uses Production's region and a region-suffixed deployment-record name, avoiding Azure's immutable deployment-location conflict without changing resource names or Staging's region. Check F1 regional availability/quota and fail rather than upgrade SKU. Before requesting keys or mutating bootstrap resources, reject an existing group whose location differs from the selected region; location changes require explicit migration/recreation and must not silently redirect identities or delete resources.

Using the authenticated GitHub CLI, bootstrap creates/updates both GitHub environments and branch policies via the GitHub API: Production permits only main; Staging permits PR refs. No persistent PAT, Azure client secret or publish profile is stored in GitHub. User supplies provider keys by hidden prompt/stdin or existing secure input; bootstrap uses `gh secret set --env <environment> DEEPSEEK_API_KEY` without echoing the value. GitHub administrative access is needed only for this bootstrap; normal Actions `GITHUB_TOKEN` is not assumed to manage environments. Document equivalent manual secret entry as an optional fallback, not the primary workflow. Nothing can manufacture the user's Azure/GitHub authorization or provider credentials.

Routine workflow: read the environment's manifest entry, authenticate by OIDC, run Bicep validation/what-if, check that changes remain within the selected RG and leave bootstrap-owned identity/RBAC resources untouched. Accept `Ignore`/`NoChange` only for the exact auto-created `Microsoft.AlertsManagement/smartDetectorAlertRules/Failure Anomalies - <selected insightsName>` resource in that same subscription/group; reject any write to that rule and any other unrecognized resource. Boundary errors report the offending resource ID and change type, never resource payloads or app settings. Then apply `main.bicep` incrementally. Stop an existing app before changes that can restart it. Prevent unintended deletes/replacements or paid SKU changes; an incremental deployment still resets omitted resource properties, so templates own the complete desired app/workspace configuration. New environment creation and redeployment must both work. The first app remains non-serving until caps/settings/package/storage initialization pass. All app settings are applied as one complete desired set, including preserved secure runtime inputs; no competing partial writers erase the provider key or Insights connection. Pass the key as an `@secure()` Bicep parameter through a restricted temporary parameter file, never command-line literals, outputs, what-if logs or artifacts. Scrub temporary files on every exit.

### 4.1 Application Insights and free-allowance controls

Bicep provisions `Microsoft.Web/serverfarms` (F1/Linux), `Microsoft.Web/sites`, `Microsoft.OperationalInsights/workspaces` (`PerGB2018`, 30-day retention), and `Microsoft.Insights/components` with an explicit `WorkspaceResourceId`, once per environment. Do not allow implicit extra workspaces, commitment tiers, diagnostic-log duplication, availability tests, paid alerts, profiler/snapshot debugger or browser telemetry. The requested free usage uses the Analytics Logs billing allowance, not a legacy Free workspace SKU.

Version the cap policy in the environment parameter files as integer MB for easy validation: **50 MB/day (0.05 decimal GB/day) per workspace and per Application Insights component**. Combined nominal ingestion at the caps is `2 × 0.05 × 31 = 3.1 GB` in a 31-day month, leaving 1.9 GB below the published 5 GB/month billing-account allowance when no other workloads consume it. The allowance is not per app, workspace or subscription. Bootstrap checks/documentation must account for other billing-account consumption where accessible; if it cannot be established, report the assumption rather than claim free usage is verified. Reduce allocations in versioned config if other workloads use the allowance; never automatically increase them.

Apply workspace `workspaceCapping.dailyQuotaGb` through Bicep where the pinned API/toolchain supports exact fractional values. Do not round 0.05 up to 1 GB because Bicep lacks floating-point literals. The automated post-provision PowerShell step sends an ARM workspace PATCH (API 2023-09-01) containing only `properties.workspaceCapping.dailyQuotaGb` as an exact JSON number, and uses `Set-AzApplicationInsightsDailyCap -DailyCapGB 0.05` for the component. Do not call `Set-AzOperationalInsightsWorkspace -DailyQuotaGb` for a fractional cap: the pinned cmdlet parameter is Int32 and converts 0.05 to zero. Read workspace cap/retention independently through ARM GET, and component cap through CurrentBillingFeatures GET. Typed fixtures must reflect the actual Int32/Double cmdlet contracts and verify serialized PATCH numbers, routing, failure behavior and readbacks. Add `scripts/azure/configure-monitoring.ps1`, pin Az module versions, and authenticate its Az context with the same environment OIDC identity (Azure login with PowerShell session enabled). For the Azure CLI bridge used by local bootstrap/deploy, pass the CLI ARM token directly as a string to `Connect-AzAccount -AccessToken` (the pinned Az.Accounts contract), validate CLI/token tenant/subscription metadata and the resulting Az context, and scope authentication to the current process with context autosave disabled. Clear token variables on success/failure; never log token values or persist them. Check both CLI commands independently and stop before any cap setters when authentication fails. Cover the actual handoff with mocked CLI/cmdlet fixtures, including the SecureString-to-string regression. Current Microsoft guidance does not expose the Application Insights component cap in Bicep; all resources are still provisioned with Bicep and no portal cap editing is required. Keep one source of truth for the numeric policy, feed both commands from it, apply on every reconciliation and read back both caps before enabling telemetry/starting the app. Stop on rejected values or unverifiable caps; do not silently use the 100 GB default. This step is part of deployment, including bootstrap/redeploy, not an optional follow-up.

Daily caps are delayed safeguards and can overshoot; excess ingestion is billable. They cannot guarantee a zero invoice. Add source-side sampling/filtering rather than using cap exhaustion as normal operation. Use fixed trace sampling (initially 10% Production, 5% Staging), warning/error-only application logs, filtered health/static requests, bounded dimensions/metrics and no duplicate agent-plus-SDK collection. Account for logs and metrics separately: trace sampling alone does not cap all telemetry. Caps stop collection until Azure's reset hour; document that loss of monitoring. Avoid costly long retention, export and additional telemetry products. Verification checks the settings and bounded ingestion without deliberately filling the caps.

Add a pinned supported Azure Monitor OpenTelemetry ASP.NET Core integration in `LinguaDesk.Api.csproj`, dependency lockfiles and an `Infrastructure/Telemetry` registration module called from `Program.cs`. Bind sampling/filter options from .NET config in code; don't assume the SDK automatically reads custom settings. Use the supported trace exporter from the pinned integration package with explicitly constructed allowlisted request/dependency/error Activities; do not subscribe raw automatic HTTP/SQL/log/metric streams for export. This keeps exception events, raw URLs and inherited baggage outside the exported stream. Enable export only in hosted profiles with a generated connection string; disable exports in all offline CI/contract/test hosts. Use an in-memory exporter for tests. A single sanitized synthetic marker with deployment SHA/environment confirms end-to-end ingestion without invoking an LLM; all normal paths apply sampling.

Telemetry is allowlisted: route templates, status, duration, opaque operation/correlation IDs, numeric cost/usage and environment/revision tags. Strip URL queries, submitted/generated text, prompts, provider responses, SQL values, email/account identifiers, cookies and authorization headers. Sanitize exception messages and dependency attributes before export; do not rely on log redaction to sanitize automatic instrumentation. Test privacy using synthetic sentinels. Disable or bound exporter disk buffering and keep any temporary buffer out of application backups. A monitoring outage must not prevent normal app operation once configuration preflight passed; cap configuration failure must block rollout before enabling collection. Hosted verification checks each marker appears only in its own component/workspace, cap readback and finite retention without generating a traffic flood or paid LLM calls.

### 5. Deployment, migration and rollback

Before mutation validate the generated identity manifest, Bicep plan/target RG, Linux/F1 configuration, distinct environment mapping, artifact identity/checksum and required secret. Run resource reconciliation and both telemetry-cap checks before enabling the new package; validate created resource IDs and returned hostnames. Stop/drain the target and ensure the old serving process is gone. Upload the local ZIP through `az webapp deploy --restart false --async false --track-status false --enable-kudu-warmup false --timeout 300000`. The target stays stopped/gated during extraction; CLI Linux runtime tracking must not wait for startup before activation. Bound the entire ZIP CLI subprocess to 330 seconds independently of its internal polling and require a numeric deployment status 4 plus `complete=true` before activation. Pending, failed, malformed, missing or timed-out completion leaves activation blocked. Report safe fixed upload/startup timeout/failure phases without raw diagnostics, app settings or secret values. Only after extraction succeeds apply enabled settings, explicitly start the app and run the separate bounded provider-free smoke. Do not delete persistent home data. Start with the deployment wrapper: backup, migrate, verify storage, start API. Empty-store creation is deliberate first initialization; an unexpectedly missing established database must fail instead of silently resetting accounts/ledger. Persist an initialization marker outside the deployment artifact and verify it on subsequent runs.

Poll `/health/live`, `/health/ready`, `/`, one known SPA deep link and `/api/capabilities` over HTTPS with bounded retries/timeouts suitable for cold starts; check missing API/assets return 404 and verify revision metadata. Do not send translation, rewriting or alternatives requests, run paid checks, or seed accounts in hosted environments. Detailed authenticated Chromium journeys run offline against the published local host. Separate Staging-only synthetic storage/recovery checks must not expose a public maintenance endpoint or reuse production data.

On failure mark deployment failed with target/SHA and sanitized reason. Keep migration failures unavailable. Do not auto-downgrade schema. Retain the prior known-good artifact and consistent pre-migration backup on the environment's private storage. Rollback procedure serializes with deploy, drains the app, verifies schema compatibility and redeploys the previous artifact. If restore is required, restore only a stopped consistent backup under explicit recovery scope; do not overwrite ledger changes accrued since the backup. Preserve unresolved monetary exposure and operation identities. Rehearse failure/rollback on isolated data before enabling both automatic targets. Bound backup retention against F1 disk quota; cleanup removes only verified superseded backups, never the sole recovery point, active database or keys.
