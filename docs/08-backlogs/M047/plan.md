# M047 — Implementation plan

Behavior: [spec](spec.md). Reviewed inputs: [manifest](context.json). Implementation is not part of this planning change.

## Execution brief

Add GitHub Actions for the existing .NET 10/React combined publish output. Provision two isolated resource groups with Bicep, one each for GitHub environments `Staging` and `Production`. Each contains a Linux F1 App Service Plan, Web App, workspace-based Application Insights component and dedicated Log Analytics workspace; never share databases, keys, telemetry or deployment identities. Deploy PR head revisions to Staging and master push revisions to Production. Use OIDC, idempotent Bicep provisioning and prebuilt ZIP artifacts; no deployment slots. Non-secret settings live in versioned configuration or are derived automatically. GitHub requires zero environment/repository variables and only one environment secret name, `DEEPSEEK_API_KEY`, with separate values for Staging and Production.

Preserve existing API contracts and UI behavior. A one-time bootstrap uses authenticated Azure CLI and GitHub CLI sessions to establish resource groups, OIDC and GitHub environments and generate non-secret deployment identifiers. Repository implementation can proceed without Azure credentials; hosted acceptance requires authorized bootstrap access and provider secret values. This rewrite remains a planning change, not an instruction to execute cloud deployment now.

## Changes and order

### 1. Linux SQLite hosting profile and release preparation

Update `StorageOptions`, persistence connection/initialization policy, deployment tooling and focused API persistence tests. Add an explicit `Storage:JournalMode` option: retain WAL for existing local deployments; select `Delete` for App Service and use `synchronous=FULL`, foreign keys and bounded busy timeout. Reject unknown modes and unexpected existing database modes before serving. Do not rewrite applied migrations.

The initial migration currently forces WAL. Build a dedicated deployment preparation mode/tool that runs before the web host, against the mounted target file: provision directories with restrictive permissions, acquire an exclusive deployment lock, retain a consistent backup, apply EF migrations, checkpoint any legacy WAL and switch to DELETE with no other connections open, assert actual journal mode and database integrity, then release the lock. Test fresh initialization and upgrades through the existing WAL-setting migration. Never serve while transient migration journal settings are active. Local normal startup still does not mutate schema; the new deployment startup wrapper explicitly invokes preparation and then `exec`s the API. Migration failure exits without starting the host. Abrupt restarts must retry safely; don't assume a graceful shutdown hook will run.

Use `/home/linguadesk/data/linguadesk.db`, `/home/linguadesk/keys` and `/home/linguadesk/backups`, outside `/home/site/wwwroot`. Keys are durable and environment-specific. Never copy the live SQLite file to ephemeral local storage and periodically sync it back. Keep a single app process/instance; serialize all deployments and prevent old/new workers from overlapping database access during restart. A simple successful smoke does not prove network filesystem durability: hosted checks must exercise contention, interruption, restart, redeployment and restore, and inspect integrity/accounting invariants. If locking/durability fails on App Service storage, leave this AC blocked and record the failure for a design decision; no automatic fallback to volatile storage or a new database service.

These are planned files, not existing commands. Reuse existing checks/publish logic instead of duplicating application builds.

Install SDK from `global.json` (currently 10.0.302), Node/npm from `frontend/package.json` (currently 24.20.0/11.11.0), locked NuGet/npm dependencies and the pinned Playwright Chromium browser plus Linux system dependencies. Use a pinned Ubuntu runner and immutable action SHAs verified at implementation. Review shell portability: current scripts were developed on macOS. Do not silently upgrade toolchains to make CI green.

The explicit offline allowlist is `bash scripts/backend.sh check`, `bash scripts/backend.sh smoke`, `bash scripts/contract.sh check`, `bash scripts/ai.sh check`, `bash scripts/ai.sh probe`, `bash scripts/frontend.sh check`, `bash scripts/frontend.sh smoke`, `python3 automation/context.py audit` and `git diff --check`, plus new deployment tests. Run setup commands first. The AI check/probe use scripted transports; preserve their credential scrub. Also check the M047 context lock while implementing this milestone; do not make all future deployment workflows depend on an indefinitely fresh historical milestone lock.

Never call `verify-access`, commands with `--live`, `m046-live`, `test:e2e-live`, or live benchmark/evaluation commands. No provider credential is available to build/check jobs. Offline means no real LLM calls; dependency downloads and Azure deployment API calls are allowed. Published browser tests use the existing isolated migrated/seeded smoke database and deterministic providers, never either hosted database. Hosted configuration must reject smoke seeding and test-provider flags.

Build with `scripts/publish.sh`; package its `artifacts/publish` contents at ZIP root, including `LinguaDesk.Api.dll` and `wwwroot/index.html`, plus the deployment preparation executable/start wrapper and a non-secret revision manifest. Validate filenames and exclude database/key/log/test artifacts. Build once per event; deploy that exact artifact in a separate job using its run ID and SHA. Retain sanitized test reports, checksums and revision metadata with bounded retention; never upload backup files or secret runtime configuration; checked-in non-secret appsettings belong in the artifact. Configure Linux .NET 10 code stack and startup command for the wrapper. Verify runtime availability during target preflight; a self-contained linux-x64 artifact is a possible explicit packaging adjustment, not an implicit version downgrade.

### 3. Events, environment routing and credential boundaries

Use `pull_request` with `types: [opened, synchronize, reopened, ready_for_review]` and no base-branch restriction, plus `push: branches: [master]`. Draft PRs also deploy on those events; ready-for-review reruns are harmless. Checkout the exact `github.event.pull_request.head.sha` for PRs, `github.sha` for master pushes. Record that revision in the artifact. Checkout must not persist credentials.

All events run offline checks with `contents: read`. Staging deployment additionally requires a same-repository head and excludes Dependabot; fork/restricted PRs report a deliberate deploy skip. Production requires `event_name == push` and `ref == refs/heads/master`. Use separate jobs with literal `environment: Staging` / `environment: Production` and explicit `needs` on successful checks/package. There is no privileged `pull_request_target` or unvalidated `workflow_run` handoff.

Deployment jobs alone receive `id-token: write`, the selected environment secret and Azure login. Read subscription/tenant/client IDs from the generated non-secret deployment manifest, not GitHub variables. Use separate identities with federated subjects `repo:<OWNER>/<REPO>:environment:Staging` and `repo:<OWNER>/<REPO>:environment:Production`; grant each identity Contributor only on its own environment resource group so it can deploy the plan, app, workspace and Insights resource. Keep identities/federated credentials in a separate bootstrap resource group; routine jobs cannot change trust, RBAC, subscription resources or the other environment. Bootstrap requires resource-creation and role-assignment permissions; routine jobs do not. A future narrower custom role must include Bicep deployment and telemetry-cap operations, not just Web App publishing. Production GitHub environment restricts deployment branches to master; Staging permits the required PR refs. Keep required-reviewer rules off for the requested automatic deployment behavior. Verify repository plan supports configured environment protections.

Use build concurrency per PR or master with cancellation allowed. Deployment concurrency is per target environment with `cancel-in-progress: false`, so migration/deploy is not killed mid-operation. Recheck PR open state/head SHA or current master SHA immediately before mutation and skip stale artifacts. Serialize stop/infrastructure update/cap configuration/app-settings/ZIP/start/smoke in that same group. PR deployment may reconcile only Staging infrastructure; Production reconciliation runs only on master pushes. Shared Staging is the latest eligible PR deployment, not one preview per PR; a summary records PR number, SHA and URL. Closing a PR must not delete shared Staging.

### 4. Bicep, configuration and automated bootstrap

Add `infra/azure/bootstrap.bicep` (subscription scope), `infra/azure/main.bicep` (environment resource-group scope), modules for App Service and monitoring, `infra/azure/staging.bicepparam`, `infra/azure/production.bicepparam`, and `scripts/azure/bootstrap.sh`. Pin supported resource API versions during implementation. Version the default region, naming prefix, F1 SKU, .NET stack, 30-day workspace retention and telemetry cap policy in these files. Derive globally unique names from subscription/resource-group/environment; consume resource IDs, hostnames and monitoring connections directly from Bicep rather than asking the user to copy them.

Bootstrap reads subscription/tenant from the active `az` context and owner/repo from `gh repo view`. It uses Bicep to create two environment resource groups, a separate deployment-identity group, user-assigned managed identities, environment-specific federated credentials and RG-scoped role assignments. It generates `infra/azure/deployment.json` with only subscription ID, tenant ID, environment client IDs and resource-group names. This non-secret manifest is intended for source control and is generated, not hand-edited; bootstrap validates it before writing and never commits/pushes automatically. Rerunning for the same subscription/repository preserves identities and names. The selected region has a versioned default and optional bootstrap flag; no portal editing is required. Check F1 regional availability/quota and fail rather than upgrade SKU.

Using the authenticated GitHub CLI, bootstrap creates/updates both GitHub environments and branch policies via the GitHub API: Production permits only master; Staging permits PR refs. No persistent PAT, Azure client secret or publish profile is stored in GitHub. User supplies provider keys by hidden prompt/stdin or existing secure input; bootstrap uses `gh secret set --env <environment> DEEPSEEK_API_KEY` without echoing the value. GitHub administrative access is needed only for this bootstrap; normal Actions `GITHUB_TOKEN` is not assumed to manage environments. Document equivalent manual secret entry as an optional fallback, not the primary workflow. Nothing can manufacture the user's Azure/GitHub authorization or provider credentials.

Routine workflow: read the environment's manifest entry, authenticate by OIDC, run Bicep validation/what-if, check that changes remain within the selected RG, then apply `main.bicep` incrementally. Stop an existing app before changes that can restart it. Prevent unintended deletes/replacements or paid SKU changes; an incremental deployment still resets omitted resource properties, so templates own the complete desired app/workspace configuration. New environment creation and redeployment must both work. The first app remains non-serving until caps/settings/package/storage initialization pass. All app settings are applied as one complete desired set, including preserved secure runtime inputs; no competing partial writers erase the provider key or Insights connection. Pass the key as an `@secure()` Bicep parameter through a restricted temporary parameter file, never command-line literals, outputs, what-if logs or artifacts. Scrub temporary files on every exit.

Keep shared application defaults in `appsettings.json`; add `appsettings.Staging.json` and `appsettings.Production.json` for deployed profiles. Include `/home/linguadesk/data/linguadesk.db`, `/home/linguadesk/keys`, new `Storage:JournalMode=Delete`, candidate/reference configuration, telemetry controls and environment-specific finite limits. Preserve the existing explicitly configured operation and monetary bounds as the starting point; do not invent a new spending authorization or reinterpret ledger units as cents. Staging uses separate credentials and its own ledger. If actual provider billing is shared, allocate the existing authorized budget across consumers before enabling paid serving; distinct databases do not enforce a shared ceiling. This is runtime configuration, not permission for CI to make provider calls.

Only platform/dynamic/secret values become Azure app settings: `ASPNETCORE_ENVIRONMENT`, `APPLICATIONINSIGHTS_CONNECTION_STRING`, `LINGUADESK_AIEVALUATION__CREDENTIALS__DEEPSEEK__APIKEY`, and required platform startup/build settings. .NET binds ordinary settings from its configuration files; environment variables override only where needed. Do not reintroduce a GitHub variable for every .NET option. Cloud proxy trust is a reviewed deployment profile generated from verified hosting inputs, not a user-maintained universal CIDR or blindly trusting forwarded headers. Test HTTPS, secure cookies and spoof rejection. Disable server-side builds and honor App Service's port contract. Do not enable Always On, slots or paid health-check features.

Add `docs/deployment/azure-app-service.md` with the bootstrap command, generated manifest handling, one secret per environment, rerun/rotation instructions and troubleshooting. Missing credentials/placeholders fail before mutating resources.

### 4.1 Application Insights and free-allowance controls

Bicep provisions `Microsoft.Web/serverfarms` (F1/Linux), `Microsoft.Web/sites`, `Microsoft.OperationalInsights/workspaces` (`PerGB2018`, 30-day retention), and `Microsoft.Insights/components` with an explicit `WorkspaceResourceId`, once per environment. Do not allow implicit extra workspaces, commitment tiers, diagnostic-log duplication, availability tests, paid alerts, profiler/snapshot debugger or browser telemetry. The requested free usage uses the Analytics Logs billing allowance, not a legacy Free workspace SKU.

Version the cap policy in the environment parameter files as integer MB for easy validation: **50 MB/day (0.05 decimal GB/day) per workspace and per Application Insights component**. Combined nominal ingestion at the caps is `2 × 0.05 × 31 = 3.1 GB` in a 31-day month, leaving 1.9 GB below the published 5 GB/month billing-account allowance when no other workloads consume it. The allowance is not per app, workspace or subscription. Bootstrap checks/documentation must account for other billing-account consumption where accessible; if it cannot be established, report the assumption rather than claim free usage is verified. Reduce allocations in versioned config if other workloads use the allowance; never automatically increase them.

Apply workspace `workspaceCapping.dailyQuotaGb` through Bicep where the pinned API/toolchain supports exact fractional values. Do not round 0.05 up to 1 GB because Bicep lacks floating-point literals. The selected deterministic fallback is the same automated post-provision PowerShell step used for the component caps: `Set-AzOperationalInsightsWorkspace -DailyQuotaGb 0.05` and `Set-AzApplicationInsightsDailyCap -DailyCapGB 0.05`. Add `scripts/azure/configure-monitoring.ps1`, pin Az module versions, and authenticate its Az context with the same environment OIDC identity (Azure login with PowerShell session enabled). Current Microsoft guidance does not expose the Application Insights component cap in Bicep; all resources are still provisioned with Bicep and no portal cap editing is required. Keep one source of truth for the numeric policy, feed both commands from it, apply on every reconciliation and read back both caps before enabling telemetry/starting the app. Stop on rejected values or unverifiable caps; do not silently use the 100 GB default. This step is part of deployment, including bootstrap/redeploy, not an optional follow-up.

Daily caps are delayed safeguards and can overshoot; excess ingestion is billable. They cannot guarantee a zero invoice. Add source-side sampling/filtering rather than using cap exhaustion as normal operation. Use fixed trace sampling (initially 10% Production, 5% Staging), warning/error-only application logs, filtered health/static requests, bounded dimensions/metrics and no duplicate agent-plus-SDK collection. Account for logs and metrics separately: trace sampling alone does not cap all telemetry. Caps stop collection until Azure's reset hour; document that loss of monitoring. Avoid costly long retention, export and additional telemetry products. Verification checks the settings and bounded ingestion without deliberately filling the caps.

Add a pinned supported Azure Monitor OpenTelemetry ASP.NET Core integration in `LinguaDesk.Api.csproj`, dependency lockfiles and an `Infrastructure/Telemetry` registration module called from `Program.cs`. Bind sampling/filter options from .NET config in code; don't assume the SDK automatically reads custom settings. Enable export only in hosted profiles with a generated connection string; disable exports in all offline CI/contract/test hosts. Use an in-memory exporter for tests. A single sanitized synthetic marker with deployment SHA/environment confirms end-to-end ingestion without invoking an LLM; all normal paths apply sampling.

Telemetry is allowlisted: route templates, status, duration, opaque operation/correlation IDs, numeric cost/usage and environment/revision tags. Strip URL queries, submitted/generated text, prompts, provider responses, SQL values, email/account identifiers, cookies and authorization headers. Sanitize exception messages and dependency attributes before export; do not rely on log redaction to sanitize automatic instrumentation. Test privacy using synthetic sentinels. Disable or bound exporter disk buffering and keep any temporary buffer out of application backups. A monitoring outage must not prevent normal app operation once configuration preflight passed; cap configuration failure must block rollout before enabling collection. Hosted verification checks each marker appears only in its own component/workspace, cap readback and finite retention without generating a traffic flood or paid LLM calls.

### 5. Deployment, migration and rollback

Before mutation validate the generated identity manifest, Bicep plan/target RG, Linux/F1 configuration, distinct environment mapping, artifact identity/checksum and required secret. Run resource reconciliation and both telemetry-cap checks before enabling the new package; validate created resource IDs and returned hostnames. Stop/drain the target and ensure the old serving process is gone. Apply settings and ZIP deployment through Azure login plus `azure/webapps-deploy` or the supported ZIP deployment API. Do not delete persistent home data. Start with the deployment wrapper: backup, migrate, verify storage, start API. Empty-store creation is deliberate first initialization; an unexpectedly missing established database must fail instead of silently resetting accounts/ledger. Persist an initialization marker outside the deployment artifact and verify it on subsequent runs.

Poll `/health/live`, `/health/ready`, `/`, one known SPA deep link and `/api/capabilities` over HTTPS with bounded retries/timeouts suitable for cold starts; check missing API/assets return 404 and verify revision metadata. Do not send translation, rewriting or alternatives requests, run paid checks, or seed accounts in hosted environments. Detailed authenticated Chromium journeys run offline against the published local host. Separate Staging-only synthetic storage/recovery checks must not expose a public maintenance endpoint or reuse production data.

On failure mark deployment failed with target/SHA and sanitized reason. Keep migration failures unavailable. Do not auto-downgrade schema. Retain the prior known-good artifact and consistent pre-migration backup on the environment's private storage. Rollback procedure serializes with deploy, drains the app, verifies schema compatibility and redeploys the previous artifact. If restore is required, restore only a stopped consistent backup under explicit recovery scope; do not overwrite ledger changes accrued since the backup. Preserve unresolved monetary exposure and operation identities. Rehearse failure/rollback on isolated data before enabling both automatic targets. Bound backup retention against F1 disk quota; cleanup removes only verified superseded backups, never the sole recovery point, active database or keys.

## Context boundaries and risks

Current repository has no `.github` workflow directory. Existing publish script already combines API/SPA; don't create a second frontend host. Existing local SQLite path policies prevent use of published output. Existing initial migration forces WAL and must be handled explicitly. Existing production-like serving checks are not equivalent to all required deployment preflight; test missing settings rather than assuming startup already rejects every omission.

UI copy/layout, language policy, wire DTOs and provider algorithms are unchanged; open their owners only if implementation affects them. Readiness is infrastructure readiness, not model acceptance. F1 quota exhaustion, cold starts, network filesystem locking and interrupted migration are explicit failure cases. No live LLM budget is needed or authorized for this milestone's CI/deployment checks. Authenticated bootstrap access, regional F1 quota and provider keys are external prerequisites; actual Azure storage, provisioning and telemetry behavior remain unverified until T006. Free telemetry usage also depends on the shared billing-account allowance and cap overshoot. Do not claim cost guarantees from template validation.
