## Scope

M010 selects the password-recovery portion of FR-002 and the M010 portions of API-AC-003, API-AC-012, API-AC-014 and V-004/V-009/V-015. M009 is complete and supplies the current Bearer [REDACTED] contract, bearer-header-wins scheme selection, and per-request current-account/security-stamp revalidation for both cookie and Bearer [REDACTED]; M007 supplies the sibling confirmation/resend pattern (strict account boundary, byte-equivalent non-enumerating acknowledgments, durable delivery cooldown, unpadded base64url wire codes). M010 adds recovery without changing those contracts.

The milestone adds two anonymous JSON operations:

- `POST /api/accounts/forgot-password` (`requestLocalAccountPasswordReset`) accepts exactly required string `email` under M006's email syntax, whitespace and 254-scalar rules. Every syntactically valid known or unknown email returns the same `202 { "status": "passwordResetRequested", "retryAfterSeconds": 60 }` shape with intentionally equivalent auth/cache/location headers. Only an existing local account outside its durable reset-delivery cooldown requests adapter delivery. Unknown accounts, accounts inside the cooldown, and delivery failures send nothing and keep the same acknowledgment. Storage/key unavailability is a sanitized `503`/`availability` result that issues no reset material.
- `POST /api/accounts/reset-password` (`resetLocalAccountPassword`) accepts exactly required strings `userId` (at most 450 characters), `code` (at most 4096 characters) and `newPassword` under M006's 15–128 well-formed Unicode scalar policy, passed to Identity exactly as supplied without trim, normalization or truncation. A valid triple durably sets the new password, rotates the security stamp, returns `200 { "status": "passwordReset" }`, issues no credential, sets no cookie, redirects nowhere and starts no language work. Unknown users and malformed, mismatched, corrupted, consumed or expired material return the same `400` Problem Details category `invalidOrExpiredPasswordReset`. A `newPassword` violating the M006 policy returns field-safe `400` validation that describes only the password constraint and applies identically whether or not the account exists.

Reset tokens use the default ASP.NET Core Identity password-reset Data Protection provider with an explicitly pinned 60-minute lifespan (selected by M010; M007 left this open). Wire codes are the unpadded base64url encoding of the UTF-8 Identity token, decoded only in the handler. Both operations reject query parameters, unknown/duplicate JSON properties, non-string values, malformed JSON/UTF-8 and non-UTF-8 `application/json` consistently with the existing strict account boundary. All responses use `Cache-Control: no-store`; wrong methods return 405 with the single allowed method.

The reset-delivery coordinator mirrors M007's delivery gate with a dedicated LinguaDesk-owned reset marker in the existing Identity `AspNetUserTokens` table: a UTC attempt marker is recorded before invoking the adapter, serialized by the existing single-process account gate; if the marker cannot be persisted, sending is suppressed and the safe result matches delivery unavailability. The fixed response always reports 60 seconds rather than revealing whether a row or remaining cooldown exists. Fake time proves cooldown and lifetime boundaries without sleeps. No new migration, queue, outbox, short-term abuse limiter or compatibility promise is introduced.

Explicit exclusions: browser reset forms/routes/safe-return/workspace teardown (M014), live email delivery/templates/public origin (M034), sign-in/out, cookie/Bearer [REDACTED] issuance, antiforgery, verification confirmation, language operations, allowances/accounting, account deletion/backup policy (Q-004), roles/admin/Google, P-005 abuse controls and P-006 compatibility guarantees. M010 does not complete full FR-002, API-AC-003 or RG-005.

## Constraints and decisions

Use real `UserManager<IdentityUser>`, the default Identity password-reset token provider, the production SQLite provider/migrations, persistent Data Protection keys and HTTP endpoints for behavioral evidence. A mocked user store, test-auth handler or manually fabricated reset token cannot establish AC-001–004. Capturing/failing reset-delivery adapters and fake time are deterministic test seams and must remain impossible to select through production configuration; the production default sends nothing.

No email address, user ID, reset code/token, password, query string, cookie, Bearer [REDACTED] key material, request body or raw Identity error may enter response detail, logs, traces, filenames, test reports or committed fixtures. Safe diagnostics contain only category/correlation/outcome. Reset material travels in a JSON body, never a query string or automatic GET mutation.

Q-006 is resolved locally only for these two operations, their token/cooldown behavior and error categories. The 60-minute reset lifetime and the `forgot-password`/`reset-password` names, fields and categories are M010 selections. Q-004 does not block this slice because the reset marker is delivery metadata in the existing Identity schema and M010 makes no deletion, backup-retention or copied-token-revocation claim. P-005 and P-006 remain proposed. No human input or live service is required; failure to restore locked dependencies or run the deterministic harness is an execution blocker, not evidence that a gate passed.
