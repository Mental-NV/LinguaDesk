## Scope

M007 selects the email-verification portion of FR-002 and the M007 portions of API-AC-003, API-AC-012, API-AC-014 and V-004/V-009/V-015. M006 is complete and supplies durable unverified ASP.NET Core Identity accounts, persistent Data Protection keys, the current-state `VerifiedAccount` policy, registration delivery intent, storage readiness, and deterministic contract generation.

The milestone adds two anonymous JSON operations:

- `POST /api/accounts/confirm-email` (`confirmLocalAccountEmail`) accepts exactly required strings `userId` and `code`. The delivery boundary supplies the opaque Identity user ID and a base64url encoding of the UTF-8 Identity confirmation token. A valid pair returns `200 { "status": "verified" }`; it durably confirms the account, remains idempotently successful when the same valid material is submitted again, issues no credential, sets no cookie, redirects nowhere, and starts no language work. Unknown users and malformed, mismatched, corrupted, or expired material return the same `400` Problem Details category `invalidOrExpiredVerification`. Storage/key unavailability is a sanitized `503`/`availability` result.
- `POST /api/accounts/resend-verification` (`resendLocalAccountVerification`) accepts exactly required string `email` under M006's email syntax, whitespace, and 254-scalar rules. Every syntactically valid known-unverified, known-verified, or unknown email returns the same `202 { "status": "verificationRequested", "retryAfterSeconds": 60 }` shape. Only a known unverified account outside its cooldown may request delivery. Concurrent/repeated calls inside the cooldown, confirmed accounts, and unknown accounts send nothing. Delivery failure retains the same 202 acknowledgment and leaves the account unverified.

Confirmation tokens use a dedicated named ASP.NET Core Identity Data Protection email-confirmation provider/options type with an explicitly pinned 24-hour lifespan and the existing `LinguaDesk` application name/key directory. M007 does not alter the default/reset token provider or choose M010's reset lifetime. Wire codes are unpadded base64url text; malformed code, empty values, user IDs over 450 characters, or codes over 4096 characters fail generically without token verification. Confirmation and resend reject query parameters, unknown/duplicate JSON properties, non-string values, malformed JSON/UTF-8 and non-UTF-8 `application/json` consistently with the existing strict account boundary. All responses use `Cache-Control: no-store`; wrong methods return 405 with the single allowed method.

The common delivery coordinator is used by both registration and resend. A delivery attempt records a UTC cooldown marker through the existing Identity `AspNetUserTokens` table under a LinguaDesk-owned provider/name before invoking the adapter, serialized by the existing single-process account gate. If that marker cannot be persisted, sending is suppressed and the safe result matches delivery unavailability; registration and resend still retain their generic accepted acknowledgments. The fixed response always reports 60 seconds rather than revealing whether a row or remaining cooldown exists. Fake time proves cooldown boundaries without sleeps. The selected single-instance topology makes the process gate sufficient; no new migration, queue, outbox, short-term abuse limiter, or compatibility/version promise is introduced.

Explicit exclusions: sign-in/out, cookies, bearer/refresh credentials, antiforgery, authenticated account-status reads, password reset, security-stamp changes, language operations, allowances/accounting, React route/form work, email HTML/provider selection, public origin/link assembly, real mailbox delivery/click evidence, account deletion/backup policy, roles/admin/Google, P-005 abuse controls, and P-006 compatibility guarantees. M008/M009/M010/M012/M034 retain those outcomes. M007 does not complete full FR-002 or RG-005.

## Constraints and decisions

Use real `UserManager<IdentityUser>`, Identity token providers, the production SQLite provider/migrations, persistent Data Protection keys, and HTTP endpoints for behavioral evidence. A mocked user store or test-auth handler cannot establish confirmation behavior. Capturing/failing delivery adapters and fake time are deterministic test seams and must remain impossible to select through production configuration.

No email address, user ID, confirmation code/token, query string, cookie, key material, request body, or raw Identity error may enter response detail, logs, traces, filenames, test reports, or committed fixtures. Safe diagnostics contain only category/correlation/outcome. The API accepts confirmation material in a JSON body, never an API query string or automatic GET mutation. The eventual M034 adapter may assemble a link for M012, but M007 does not select a public origin or claim live delivery.

Q-006 is resolved locally only for these two operations and their token/cooldown behavior. Q-004 does not block this slice because the cooldown marker is account-lifecycle metadata in the existing Identity schema and M007 makes no deletion, backup-retention, or revocation claim. P-005 and P-006 remain proposed. No human input or live service is required; failure to restore locked dependencies or run the deterministic harness is an execution blocker, not evidence that a gate passed.
