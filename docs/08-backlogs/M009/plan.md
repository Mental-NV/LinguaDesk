## Migration, rollout and rollback

No migration is expected; pending-model checks must remain green. Bearer tickets are protected with the existing stable application name/keys and add no database rows or text retention. Serving retains M006 readiness: an explicitly migrated database and usable persistent key directory are required; contract generation remains free of database/key/listener effects.

Tokens are opaque secrets the client stores and presents; there is no server allowlist to roll back per token. Existing pairs expire at most seven days after issue and become invalid if keys are deliberately rotated or stamps change. Rollback removes the three routes/bearer configuration while retaining compatible account/key/cookie data; never delete accounts or keys as rollback cleanup. Discarding held credentials ends ordinary local use; copied-token revocation beyond the stamp rule remains unclaimed.

## Context boundaries and risks

UX routes, focus, messages, safe-return handling and workspace clearing are referenced only to preserve the later M013 contract; no React or browser acceptance is selected. M010 owns reset and its stamp mutation; Q-004 owns deletion/backup/further revocation guarantees. LLM, operation/accounting/cost, provider, quality and performance domains are irrelevant because these routes cannot submit text or call a provider. No AI specification or accounting contract belongs in the execution packet.

Principal risks and controls:

- Framework bearer defaults may not pin the 15-minute/7-day lifetimes or validate stamps per request. Pin every lifetime option, validate current account/stamp on each bearer access and refresh, and assert exact injected-time boundaries.
- Custom refresh can become a hand-rolled token scheme. Use the framework's bearer-token protection purposes, validate through the real handler, and prove invalid/expired/stale refresh rejection.
- Scheme selection can silently merge principals or fall back. Keep the explicit forward selector, authenticate exactly one scheme per request, expose `authMode`, and test both precedence directions.
- Sign-in/refresh can enumerate accounts or leak tokens. Use one invalid-credential result, disclose verification only after password success, expose tokens only in the issuing body, and test response/header/log equivalence plus token sentinels.
- Contract generation could instantiate storage/keys or omit bearer security requirements. Preserve the existing generation branch, review actual security metadata and assert zero effects separately from runtime semantics.
- Refresh is not revocation of copied tokens. State that boundary explicitly; test stamp/deletion invalidation and leave per-device revocation to its owner.

Human actions: None. Routine restores, owned temporary databases/keys/certificates and deterministic local hosts suffice. Missing locked dependencies, an unavailable real bearer integration path or a required lifecycle decision blocks only its affected gate and must be recorded rather than replaced by a fake pass.

Readiness review: M008 is satisfied; exact selected operations and error/security boundaries are fixed; every AC maps to ordered work, a runnable deterministic check and evidence target; contract generation precedes handler completion; no blocking question or human gate remains; omitted domains have explicit owners.
