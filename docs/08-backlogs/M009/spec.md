## Scope

M009 selects the bearer portion of FR-001/FR-036, API-AC-002/003/012/014 and V-004/V-009/V-015. M008 is complete and supplies the current cookie-session contract, antiforgery bootstrap, eight-hour `__Host-LinguaDesk.Session` policy, per-request stamp revalidation, bearer-header no-fallback rejection, strict account parsing and generated-contract ordering. M009 adds bearer issuance/refresh with ASP.NET Core Identity's protected opaque bearer-token format. It replaces the M008 `LinguaDesk.UnsupportedBearer` rejection with real bearer authentication while keeping cookie precedence rules.

The milestone adds three account operations with these stable names and wire boundaries:

- `POST /api/accounts/bearer-sign-in` (`signInBearerClient`) is anonymous, needs no antiforgery, and accepts exactly required string fields `email` and `password` with the same M006/M008 rules: M006 syntax, password passed to Identity exactly as supplied without trim, normalization or truncation. Valid credentials return `200 { "accessToken": "...", "refreshToken": "...", "expiresIn": 900, "tokenType": "Bearer" }` where expiries come from the injected time source: access exactly 15 minutes, refresh exactly seven days. The tokens are opaque protected secrets exposed only in this body; they are never set as cookies, never logged, and never appear in any other response, header, log or fixture. Unknown email and wrong password return the same `401` Problem Details category `invalidCredentials` with no token, no account detail, no password echo and `Cache-Control: no-store`. Only valid credentials may disclose `verificationRequired` elsewhere; bearer sign-in of a valid unverified account returns the pair plus `verificationStatus: verificationRequired` while the existing `VerifiedAccount` policy still denies language admission. Storage/key/signing failure is a sanitized `503`/`availability` result that issues no usable credential.
- `POST /api/accounts/bearer-refresh` (`refreshBearerClient`) is anonymous, needs no antiforgery, and accepts exactly required string fields `refreshToken` and `accessToken` (the currently held pair; both present so a stolen refresh alone is insufficient). Valid non-expired credentials whose account still exists with a current security stamp return `200` with a replacement pair of the same shape, issued at the current injected time with the same 15-minute/7-day lifetimes. The refreshed pair replaces the held pair; refresh never replays a language operation and claims no single-use rotation or replay detection beyond Identity's standard protection. Invalid, expired, malformed, account-deleted or stamp-stale credentials return the same secret-free `401` category `authenticationRequired` with no replacement pair. Refresh validates expiry, current account and security stamp before issuing anything; invalid/expired refresh requires a fresh sign-in.
- `GET /api/accounts/me` (`getCurrentAccount`) accepts either a valid `Authorization: Bearer ...` credential or a valid session cookie under existing scheme selection, and returns `200 { "email": "...", "verificationStatus": "verified" | "verificationRequired", "authMode": "bearer" | "cookie" }`. It reports which credential mode authenticated the call so consumers can prove precedence. Missing, expired, malformed, deleted or stamp-invalid credentials return the same no-store `401` category `authenticationRequired` with no account data and never an HTML redirect. Bearer and cookie responses are `Cache-Control: no-store`.

Credential precedence and validation, unchanged and extended from M008:

- Authentication runs before authorization. If a request contains an `Authorization: Bearer ...` header, only the bearer scheme authenticates it; an invalid bearer token must never fall back to an ambient valid cookie, and a request with no bearer header may use cookie authentication. Principals from different accounts are never combined. `GET /api/accounts/me` exposes this selection observably via `authMode`.
- Every accepted bearer access and every refresh validates that the account still exists and its credential security stamp is current, on that request, beyond signature/expiry validation. Password reset (M010) or any stamp change therefore makes previous access/refresh credentials unacceptable to subsequent protected requests. Do not rely on bearer expiry alone. An already admitted operation may still settle within its deadline under architecture §7; revocation does not restore text or reverse a charge.
- Bearer clients end ordinary local use by discarding their credentials; this is not server revocation of a copied token. No per-device session/token-revocation API, account deletion UI, single-use refresh rotation, JWT/OIDC/OAuth construction or client-registration server is added. Cookie sign-out behavior is unchanged: clears only the caller's cookie, changes no stamp, and the SPA still clears workspace text immediately even if confirmation is lost. Bearer calls never require the browser antiforgery pair; cookie mutations still require it.
- Strict JSON/media/query/method boundaries mirror M008: POST-only sign-in/refresh, GET-only `me`, 405 with the single allowed method otherwise, no query parameters, UTF-8 `application/json` only, unknown/duplicate properties rejected, secret-free Problem Details without email, password, token, cookie, request token, user ID, stamp, query string or raw Identity errors. All account responses are non-cacheable. Sign-in and refresh accept bearer use without cookies; cookie-authenticated state changes still require antiforgery.

Explicit exclusions: password reset or stamp mutation UI (M010), browser forms/routes/safe-return/workspace teardown (M013), language operations, allowances/accounting, live email (M034), roles/admin/Google/OAuth/OIDC/JWT construction, per-device revocation API, account deletion semantics (Q-004), P-005 attempt controls and P-006 compatibility guarantees. M009 does not complete full FR-001/FR-036, API-AC-002/003, RG-005 or any release gate.

## Constraints and decisions

Use the real ASP.NET Core Identity bearer-token handler, password verifier, security stamps, production SQLite provider/migrations and persistent Data Protection keys. A test-auth principal, mocked user store, manually fabricated bearer value or synthetic stamp check cannot establish AC-001–004. Focused tests use fake time and owned HTTPS/file-backed fixtures; no sleep or public service is needed.

No email, password, access/refresh token, cookie/ticket, antiforgery token, user ID, security stamp, query string or raw Identity exception may enter response details, logs, traces, filenames, test reports or committed fixtures. Safe diagnostics contain only category, correlation and classified outcome. All account responses are non-cacheable; this slice persists no new account, session or text data and needs no migration or package beyond Identity's standard bearer protection (no new EF migration expected; Data Protection keys reuse the existing boundary).

Q-006 is resolved locally for these three operations, names, fields, token shape, precedence and error categories. Q-004 does not block the bounded bearer behavior: M009 claims only credential issuance/validation under the stamp rule, not account deletion semantics, backup retention or revocation of copied tokens. P-005/NFR-008 and P-006 remain proposed, so no attempt limiter, rotation policy or version guarantee is introduced. Human/live browser evidence belongs to M013 and is not replaced by deterministic API tests.
