# API account behavior

Authoritative continuation of [05-api-design.md](../05-api-design.md); section numbers refer to that document; read only when relevant to the selected scope.

## 3. Authentication, verification, and account lifecycle

### 3.1 Cookie and bearer access

Use ASP.NET Core Identity for local accounts and select its protected opaque bearer-token format for independent clients. The SPA uses a Secure, HttpOnly session cookie with SameSite=Lax, server-side expiry and no persistent “remember me” option. Browser JavaScript does not receive or persist access/refresh tokens. Independent clients receive bearer access and refresh tokens and treat them as opaque secrets; no JWT parsing, OIDC discovery, OAuth delegation or client-registration server is promised. Microsoft documents both Identity modes and that its bearer tokens are proprietary rather than JWTs. [Identity API authorization](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0)

Each sign-in selects one credential mode explicitly. If a request contains a bearer Authorization header, authenticate that scheme only; an invalid token must not fall back to an ambient cookie. Without that header, cookie authentication may apply. Do not combine principals from different accounts. The selected auth slice documents this choice in OpenAPI security requirements and tests the actual handlers.

Cookie-authenticated state changes, including sign-in/sign-out where relevant, require antiforgery validation. Supply an anonymous bootstrap mechanism for the SPA to obtain the request token and renew it after identity changes. SameSite and JSON content type alone are not the antiforgery contract. A bearer-only call that ignores cookies does not require a browser antiforgery token. The precise bootstrap operation/header/cookie names belong to the auth slice. [ASP.NET Core antiforgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0)

### 3.2 Expiry, refresh, and revocation

Initial engineering settings are an 8-hour server cookie lifetime with sliding renewal disabled, 15-minute bearer access lifetime and 7-day refresh lifetime. Pin them explicitly in the auth configuration and disclose expiry information relevant to the client; changing them requires auth/UX regression checks. They are technical settings, not a new product SLA. Browser session-cookie removal on close is browser-controlled; the existing per-tab text teardown applies regardless of whether authentication is restored.

Refresh validates the protected refresh credential, expiry, current account and security stamp before issuing replacement credentials. Clients replace their held pair on success. Do not claim single-use refresh tokens or replay detection from standard Identity behavior; additional token-rotation policy would need its own design. Refresh never replays a language operation. Invalid/expired refresh requires sign-in. Concurrent refresh handling and the exact response fields are verified in the selected auth slice.

Every authenticated API access checks that the account still exists/is enabled and that its credential's security stamp is current. This is a LinguaDesk authorization requirement beyond merely validating the token's signature/expiry; implement and test it for both cookie and bearer schemes. Password reset or administrative account revocation changes the stamp, making previous access/refresh credentials unacceptable to subsequent protected requests. Do not rely on a default cookie validation interval or bearer expiry to meet this check. An already admitted operation may still settle within its existing deadline under #3; revocation does not restore its text or retroactively reverse a successful charge.

Cookie sign-out clears the caller's cookie; the SPA immediately clears workspace text even if server confirmation is lost, as UX #2 requires. Bearer clients end ordinary local use by discarding their credentials; this is not server revocation of a copied token. A per-device session/token-revocation API and account deletion UI are not added here. Q-004's selected account design must define deletion and any further logout/revocation guarantees before claiming them. Account-wide revocation and password-reset invalidation follow the security-stamp rule above.

### 3.3 Verification and recovery

Under the temporary DF-008 substitute, every newly created local account is durably marked verified without proving ownership of its email address. Registration sends no email, issues no cookie or bearer credential and directs the user to sign in explicitly. Existing unverified accounts remain denied at language admission by fresh durable state; valid credentials may still disclose their unverified status through the retained account-status behavior.

Real email-address confirmation and password-reset delivery are deferred under DF-008. The implemented confirmation, resend, forgot-password and reset contracts remain dormant for later reactivation, with unavailable production senders and their existing non-enumeration/redaction behavior. They do not make email recovery available in the current MVP and do not run during registration.

M006 fixes the shared local password policy at 15–128 well-formed Unicode scalar values inclusive. Spaces and otherwise valid Unicode are allowed; do not trim, normalize or truncate, and require no uppercase/lowercase/digit/symbol composition. Hash the exact accepted string through Identity. This necessary credential contract neither selects a breached-password blocklist/attempt rate nor claims NIST conformance; proposed abuse controls remain P-005 work. M007 fixes only the email-confirmation lifetime and resend cooldown below; M010 fixes the password-reset lifetime at 60 minutes on the default Identity password-reset provider and maps anonymous `POST /api/accounts/forgot-password` (`requestLocalAccountPasswordReset`, exactly required `email`, fixed `202 { "status": "passwordResetRequested", "retryAfterSeconds": 60 }` acknowledgment) and `POST /api/accounts/reset-password` (`resetLocalAccountPassword`, exactly required `userId`/`code`/`newPassword`, `200 { "status": "passwordReset" }` on success, generic `400 invalidOrExpiredPasswordReset` otherwise, field-safe `400` for `email`/`newPassword` policy failures). A completed reset rotates the security stamp without issuing credentials. The UI uses this actual policy rather than framework sample defaults. API authentication failures return machine-readable 401/403 responses, never login-page redirects; UX controls navigation and workspace clearing.

### 3.4 M006 registration contract

M006 maps only anonymous `POST /api/accounts/register` (`registerLocalAccount`). The request contains exactly required `email` and `password` strings; no API confirmation-password, role, account ID or requested verification state exists. Email is at most 254 Unicode scalar values, has no surrounding whitespace, passes .NET's `EmailAddressAttribute` check and is unique by Identity's invariant uppercase normalized lookup. No DNS/deliverability or plus-address/domain rewriting is implied. Unknown/duplicate JSON properties, invalid encoding/shape/content type, invalid email and password-policy failures create no account or delivery. Field errors expose only `email`/`password`, never submitted values. M006 errors use standard Problem Details members plus extensions `category`, `correlationId` and, for field failures, `errors` mapping each allowed field name to an array of messages. All registration responses declare `Cache-Control: no-store`.

A new email creates one durable standard Identity account with `EmailConfirmed = true` and requests no confirmation delivery. Return `202` JSON with only `status = signInRequired` and `Cache-Control: no-store`; issue no cookie, bearer/refresh credential, account ID, email or confirmation material. Registration never signs in, redirects or invokes language work. This automatic verification is the temporary DF-008 substitute and does not prove address ownership.

A sequential, case-variant or concurrent request for an existing normalized email returns the identical `202` status/body/cache/auth shape, creates no second account, changes no existing verification state and requests no delivery. In particular, a duplicate request cannot be used to verify another person's pre-existing unverified account. The contract does not guarantee perfect transport timing equivalence, but no intentional response/header/log distinction may enumerate account membership.

The named `VerifiedAccount` policy loads current Identity state and denies missing/deleted or unconfirmed accounts; it does not trust a stale verification claim. Any future disabled-account state needs its owning lifecycle design. Data Protection/key persistence and database/key startup/readiness are owned by architecture Section 5.1. M034 owns the automatic-verification substitute; DF-008 owns reactivation of real email.

### 3.5 M007 confirmation and resend contract

M007 maps anonymous `POST /api/accounts/confirm-email` (`confirmLocalAccountEmail`) and `POST /api/accounts/resend-verification` (`resendLocalAccountVerification`). Confirmation accepts exactly nonempty string `userId` (at most 450 characters) and `code` (at most 4096 characters) in JSON. The code is the unpadded base64url encoding of the UTF-8 Identity token and is decoded only in the handler. A valid pair returns `200 { "status": "verified" }`; replaying the same valid material remains successful. Unknown users and malformed, mismatched, corrupted or expired material use the same `400` `invalidOrExpiredVerification` category. Confirmation neither issues credentials nor redirects.

Resend accepts exactly string `email` under M006's email rules. Every syntactically valid known-unverified, known-confirmed or unknown email returns byte-equivalent `202 { "status": "verificationRequested", "retryAfterSeconds": 60 }` content and intentionally equivalent auth/cache/location headers. Only an unverified account outside its durable cooldown requests delivery. Resend records the UTC attempt marker in `AspNetUserTokens` before delivery; registration no longer records that marker. Failed delivery is not retried automatically. Storage/key failures use sanitized availability behavior, while delivery failure never exposes membership. All responses are `Cache-Control: no-store`; query parameters, unknown/duplicate properties, invalid UTF-8/media and wrong methods follow the strict account boundary.

Email confirmation uses the named `LinguaDeskEmailConfirmation` Data Protection token provider with a 24-hour lifetime. The default/password-reset provider is unchanged. The deterministic adapter payload is destination, opaque user ID and base64url code; the runtime default sends nothing. M007/M012 retain historical contract/link-consumption evidence; DF-008 owns any future public-origin/template/provider/live-mail work.

### 3.6 M008 browser-session contract

M008 maps anonymous `GET /api/accounts/antiforgery` (`getAccountAntiforgeryToken`), antiforgery-protected `POST /api/accounts/sign-in` (`signInLocalAccount`), cookie-authenticated `GET /api/accounts/session` (`getLocalAccountSession`) and antiforgery-protected idempotent `POST /api/accounts/sign-out` (`signOutLocalAccount`). Bootstrap returns only `requestToken` plus fixed `headerName = X-LinguaDesk-Antiforgery` and sets the Secure/HttpOnly/Strict `__Host-LinguaDesk.Antiforgery` cookie. Sign-in accepts exactly `email` and exact, unmodified `password`; valid credentials issue only the Secure/HttpOnly/Lax nonpersistent `__Host-LinguaDesk.Session` cookie and return signed-in, verification and UTC ticket-expiry state. Unknown email and wrong password share `401 invalidCredentials`; unverified status is disclosed only after a valid password.

The protected ticket has a fixed eight-hour lifetime with no sliding renewal. Session reads return its original expiry, emit no renewal cookie, and reject missing, malformed, expired, deleted-account or stale-security-stamp credentials as `401 authenticationRequired`. A Bearer Authorization header never falls back to the ambient cookie. Sign-out clears only the caller cookie, returns 204 for authenticated or already signed-out callers with a current antiforgery pair, and does not change the security stamp. Account responses remain no-store and strict for query, JSON/UTF-8/media, shape and method boundaries. M009 retains bearer issuance/refresh, M010 reset/stamp mutation, and M013 browser routing/workspace teardown evidence.
