# ADR-014 — Catalog-driven multilingual expansion

**Status:** Selected design, 2026-10-26; PRD D-24. Implementation pending M046.

## Context

The user requests all investigated low-effort languages for Translator and Write, then clarifies that Translation should use a common template and representative evaluation instead of exhaustive all-pairs live testing. The current implementation repeats four IDs in catalog, contracts and prompts; Unicode transport, accounting, provider chains and capability-driven selectors already generalize. [Investigation](../research/language-expansion-2026-10-26.md) records concrete paths and external references.

## Decision

Select the [124-language product catalog](../product/languages.md), using one Core descriptor set and deterministic distinct-pair construction. Retain the generated C# → OpenAPI → TypeScript workflow and assert catalog/enum/mapping parity. Add scoped RTL presentation, script fonts and a versioned conservative sentence-boundary policy. Keep two shared model chains, direct translation, nine writing modes and the existing scalar/count/privacy/accounting rules. No per-language service, database catalog, pivot or routing engine is introduced.

Validate Translation's common template with fixed representative directions plus lightweight per-language anchor smokes; all pairs receive deterministic catalog checks only. [Verification §5.5](../verification/llm-evaluation.md#55-expanded-language-matrix-d-24) owns the exact matrix, thresholds, impact-based reuse and bounded failure-triggered expansion. Deep results do not establish measured quality for untested pairs. Both features still offer the complete selected catalog; failures stay explicit rather than creating undocumented operation-specific lists.

## Consequences

Adding another language becomes mostly data, prompt metadata, generated-contract and evidence work. The first expansion also needs shared RTL and punctuation changes. Native selectors remain viable; a custom search control is not required. Three-letter codes are supported deliberately. Prompt size, generated capability size and font coverage need measurement. Advanced script/dialect controls and provider routing remain separate scope.

Template-based evidence avoids quadratic paid evaluation while accepting unsampled-pair uncertainty explicitly. Low-resource quality and close-language identification remain risks. No public provider capability claim replaces required observations, and no completed four-language package is rewritten or recertified. PRD/UX/architecture/API/AI/verification documents own current contracts; this record owns rationale only.
